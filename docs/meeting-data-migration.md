# 會議資訊匯入規則

本文件供後續執行資料匯入的 agent 沿用。來源入口為[學生議會「會議資訊」目錄](https://sc.video.nccu.edu.tw/dir/1085)；每次從指定會期、會議類別與會議的子目錄讀取實際資料，不把目前目錄中的會期或場次當作固定清單。本文只規定資料判讀與寫入原則，不規定中介檔格式。

## 匯入範圍與對應

| 來源 | 目標資料 | 規則 |
| --- | --- | --- |
| 會期目錄，例如 `27-1` | `sessions` | 使用既有數字代碼，例如 `27-1` 對應 `271`；先查重再建立。 |
| `大會`或委員會目錄下的單場會議 | `meetings` | 大會的 `committee_id` 為 `NULL`、`meeting_type_name` 為 `大會`；委員會會議對應同名 `committees`。保留來源會議名稱、臺北時間的開始時間及地點。 |
| 會議議程中的議案 | `proposals`、`proposal_meetings` | 依來源內容判定討論案、報告案或選舉案；一筆議案可排入多場同會期、同委員會的會議。 |
| 議程順序及非議案文字 | `meeting_agenda_entries` | 依來源章節與順序寫入；只有已排入該會議的議案可作為議案項目。 |
| 議案原本附有的檔案或連結 | `proposal_attachments` | 保留可辨識的附件名稱及原始 HTTP(S) 連結，對同一議案按 URL 去重。 |

來源的**議案原頁面不是附件**。不要為它建立 `proposal_attachments` 記錄；會議頁或議程頁也不應批次掛到每筆議案。來源 URL 可記在當次匯入紀錄中，供日後追溯。會議議程文件只有在它原本就是某筆議案的附件時，才掛到該議案。

## 提案人與缺漏資料

- 優先使用議案原文或正式提案文件明載的提案人，對應既有 `users` 記錄；建立新使用者前先查重。`proposer_id` 必須指向 `users.id`。
- **沒有提案人的報告案，一律以「秘書處」為提案人**。使用或建立名稱為 `秘書處`、角色為 `secretariat_admin` 的使用者記錄，不使用「未載明提案人」佔位。
- `users.email` 必填且不可重複；本機新增匯入用帳號時使用唯一的 `.invalid` 地址，避免誤寄真實郵件。若要匯入正式資料，先對應已確認的既有帳號或電子郵件。
- 其他類型若仍無法查明提案人，記下來源與缺漏，待確認後再匯入該案；不要推定議程中提到的人就是提案人。
- 只匯入來源可證實的連署資料。不要為了填滿畫面建立模擬連署，也不要把「等 N 人」推成 N 筆已確認連署。
- `proposed_at` 與 `proposal_deadline_at` 在現有結構中必填。先找正式日期或截止時間；來源未載時，前者可暫用原議案頁的建立日期，後者可暫用會議開始時間，並在當次匯入紀錄逐筆標明這是技術性代值，不能稱為正式提案日或截止時間。若連可追溯的日期也沒有，先記錄缺漏，不憑空填入。
- 現有案型僅有 `discussion`、`report`、`election`。不屬於議案的質詢、工作報告或議程文字，保留為議程文字；無法確定分類時先記錄待確認，不硬歸入某案型。

## Agent 執行順序

1. 先讀本文件、[資料庫結構](./database-schema.md)及[議案與 API 規則](./d1-bills.md)，確認本次要處理的來源子目錄與目標資料庫。未明確要求時只在本機資料庫匯入，不操作正式資料。
2. 逐層檢視來源目錄、會議頁、議程及議案頁，建立本次會期、會議、議案、原始附件與來源 URL 的對照紀錄。來源 URL 只用於追溯及查重。
3. 先查既有會期、委員會、使用者與會議，再建立缺少的記錄；以會期、會議類別、名稱和時間辨識同一場會議，避免重跑後重複新增。
4. 逐案確認案型、提案人、案由、說明及附件。相同來源議案跨會議出現時，沿用同一筆 `proposals` 並新增排案關聯；若文件或內容確實是不同版本，分開記錄並在匯入紀錄寫明依據。
5. 排案後依原議程建立 `meeting_agenda_entries`，保留報告、選舉、討論等章節及非議案文字的順序。確認每個議案項目只出現一次且已排入該會議。
6. 比對來源與結果的會議、議案、排案及**原始附件**數量；檢查重複資料、空提案人、報告案連署、錯誤會期／委員會關聯，以及 `PRAGMA foreign_key_check`。在當次匯入紀錄列出代值、略過項目與尚待確認的資訊。

舊本機匯入腳本與暫存紀錄可能採用不同規則；後續匯入以本文件為準。資料庫結構無來源頁欄位，因此追溯資訊放在匯入紀錄，不借用附件欄位。
